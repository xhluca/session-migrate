# Additional native targets: Pi, OpenCode, and Cursor

This document records the content-free reverse engineering, implementation contracts, and
native validation for three requested conversion targets. All fixtures and probes use synthetic
markers. No real transcript text, session identifier, or user-specific store path is committed.

## Capability decision

| Target | Version inspected | Native import target | Decision |
| --- | --- | --- | --- |
| Pi coding agent | 0.80.6 | Documented v3 JSONL plus `--session FILE` | Supported |
| OpenCode | 1.17.20 | Documented JSON export/import bundle plus `opencode import FILE` | Supported |
| Cursor Agent CLI | 2026.03.20-44cb435 | None documented or schema-supported | Unsupported; fail closed |

“Supported” here means more than producing plausible-looking JSON. The generated bytes pass a
local structural validator and the pinned target CLI loads them using its public interface. The
native tests are authentication-free and isolated from normal user stores.

## Public adapter contracts

The leaf adapters are `session_bridge.formats.pi` and `session_bridge.formats.opencode`. Each
module exposes:

- `serialize(session, ..., session_id, cwd) -> (bytes, dropped)`;
- `parse(path)` for a portable semantic projection used by independent verification;
- `validate_native_bytes(data, session_id)`, which rejects malformed UTF-8, invalid native
  metadata, identifier mismatches, and broken structural references before publication;
- a pinned target version constant and a native-import capability constant.

Serialization is pure. It does not start another CLI, write a target database, modify a normal
agent home, or make a network request. Native importing remains an explicit operation.

The `dropped` dictionary is an exact counter keyed by the reason for every unsupported event or
field. A conversion caller can therefore require a zero-loss result or present the precise losses
before writing an artifact.

## Pi 0.80.6

### Native contract

Pi documents an append-only v3 JSONL session. The first record is a header:

```json
{"type":"session","version":3,"id":"synthetic-id","timestamp":"2026-08-18T12:00:00Z","cwd":"/synthetic/work"}
```

Every later entry has an `id`, `parentId`, RFC 3339 `timestamp`, and `type`. The bridge emits a
single linear parent chain containing:

- `message` entries for user, assistant, and tool-result messages;
- a `compaction` entry for a portable summary;
- a final `session_info` entry when the source has a title.

The writer preserves user/assistant text, inline base64 GIF/JPEG/PNG/WebP images, tool names,
tool-call identifiers, object arguments, tool-result text and images, error state, timestamps,
model, provider, and the session name. Assistant usage is initialized to zero because the source
formats do not expose a reliably portable Pi billing record.

Pi compaction requires `firstKeptEntryId`. A converted summary uses its own compaction entry ID as
the anchor, meaning all earlier entries remain auditable in the JSONL but none are replayed after
the summary. Pi 0.80.6 accepted this representation and constructed the effective context as the
summary followed by post-compaction entries.

### Location and resume behavior

The most robust handoff is an explicit path:

```console
pi --session /path/to/converted.jsonl
```

Pi also has a documented default store below `PI_CODING_AGENT_DIR`, normally `~/.pi/agent`. Its
relative session path is:

```text
sessions/--<resolved-cwd-with-separators-replaced-by-dashes>--/<UTC-millisecond-stamp>_<session-id>.jsonl
```

`pi.session_relative_path()` computes that relative path. An explicit `--session` avoids relying
on discovery naming and is preferred for initial verification.

Opening an existing file can append normal Pi state. In the pinned probe, startup appended a
`thinking_level_change`; the RPC name mutation appended `session_info`. Native validation thus
asserts that all generated records remain an exact prefix and permits only expected native suffix
entries.

### Native oracle

`tests/test_additional_formats_native.py` starts Pi 0.80.6 with:

```text
--mode rpc --offline --no-extensions --no-skills --no-prompt-templates
--no-context-files --session <synthetic-file> --session-dir <isolated-dir>
```

The test calls public RPC operations `get_messages`, `get_entries`, and `set_session_name`. It
checks all of the following:

- the compacted effective context begins with `compactionSummary`;
- post-compaction user/assistant text and image blocks survive;
- the tool call, object input, correlated tool result, result image, and final response survive;
- the complete generated entry sequence remains an exact on-disk prefix;
- only the expected Pi-owned suffix types are appended.

The test never sends a prompt to a model and sets `PI_OFFLINE=1`, so no provider authentication is
required.

## OpenCode 1.17.20

### Native contract

OpenCode publicly supports `opencode export [sessionID]` and `opencode import <file>`. Its JSON
bundle has this top-level structure:

```json
{
  "info": {"id": "ses_synthetic", "directory": "/synthetic/work", "time": {}},
  "messages": [{"info": {}, "parts": []}]
}
```

The bridge follows the 1.17.20 implementation schema rather than writing the internal database:

- session `info` includes ID, slug, directory, title, version, and millisecond timestamps;
- user message `info` carries the agent and `{providerID, modelID}`;
- assistant message `info` carries its parent, model/provider, path, completion state, and
  zero-initialized cost/token values;
- text uses `text` parts and inline images use `file` parts with data URLs;
- a tool call and its result share one assistant `tool` part whose state becomes `completed` or
  `error`;
- compaction uses the native user `compaction` trigger followed by an assistant message marked
  `summary: true`.

Tool-result images are stored in the completed state's `attachments`. Pending calls remain pending
when no matching result exists. Missing, orphaned, and duplicate call IDs are accounted for in the
loss report rather than silently ignored.

### Import and store behavior

The supported installation operation is:

```console
opencode import /path/to/converted.json --pure
```

The command returns the imported session ID. It can then be checked and resumed with public
commands:

```console
opencode session list --format json --pure
opencode export <session-id> --pure
opencode run "follow-up" --session <session-id> --pure
```

OpenCode chooses its own storage root through its normal configuration and XDG environment. The
bridge deliberately does not compute a database path or write SQLite. Tests isolate `HOME`, all
four `XDG_*_HOME` variables, and `OPENCODE_CONFIG_DIR`, then let the official importer own every
database mutation.

The model attached to the newest imported user message must be available when OpenCode resumes the
session. The adapter therefore accepts explicit `provider_id` and `model_id` values; callers should
select values configured in the destination OpenCode installation.

### Native oracle

The OpenCode 1.17.20 test performs a complete, authentication-free handoff:

1. Serialize and byte-validate a synthetic session with text, inline image, tool call, tool result,
   result attachment, and final assistant text.
2. Run the official `opencode import` command in an isolated XDG/HOME tree.
3. Find the exact session through `opencode session list`.
4. Export it through `opencode export`, revalidate the native bundle, and check the tool result.
5. Resume it with a synthetic follow-up against a loopback OpenAI-compatible HTTP server.
6. Inspect the loopback request to prove the prior history was actually replayed to the model.
7. Export again and prove the follow-up plus synthetic native reply were appended to the same
   session.

This distinguishes a genuinely resumable import from a file that merely parses.

## Cursor Agent CLI: deliberately unsupported

Cursor Agent CLI 2026.03.20-44cb435 can list existing conversations and resume the latest or a
specific chat. Its official command reference documents `cursor-agent ls`, `cursor-agent resume`,
and `cursor-agent --resume <chat-id>`. It does not document a transcript import, JSON export, session
creation API, or supported on-disk schema.

A content-free inspection of the installed binary found a workspace-scoped local database under a
shape equivalent to:

```text
CURSOR_CONFIG_DIR/chats/<hash-of-working-directory>/<chat-id>/store.db
```

The observed SQLite container used `user_version=1`, `blobs`, and `meta`, but the conversation was
an opaque proprietary agent-key/value blob graph rather than a documented relational transcript.
Knowing container and table names is not an import contract. Directly synthesizing those blobs
could corrupt state or stop working on any Cursor release.

Consequently the project fails closed:

- there is no `formats/cursor.py` writer;
- no conversion path claims Cursor support;
- tests assert the writer's deliberate absence and this documented rationale;
- a Cursor writer should be added only after Cursor publishes an import API or a versioned native
  schema that can be validated with an authentication-free resume oracle.

## Mapping and loss policy

Both supported writers preserve portable text, supported inline images, tool calls/results,
compaction summaries, timestamps, title, working directory, and model selection. The following are
reported as losses when present:

| Loss key pattern | Meaning |
| --- | --- |
| `thinking` | Private reasoning is not copied into a new target transcript |
| `message:privileged_role` | System/tool-role free text has no safe equivalent |
| `context:privileged_image` | An image on a privileged role is not replayed as user input |
| `context:image` or `tool_result:image` | Image is remote, malformed, or uses unsupported media |
| `tool_call:missing_id` / `tool_result:missing_id` | A synthetic correlation ID was required |
| `tool_result:orphan_id` / `tool_result:duplicate_id` | Source tool correlation is inconsistent |
| `tool_call:namespace` | Source-specific tool namespace is omitted |
| `timestamp:invalid` | Invalid source time was replaced by the session fallback |
| `compaction:boundary_metadata` | Summary text survived but source-private boundary metadata did not |
| `opaque:*` | Unrecognized source record has no native target representation |

The parsers keep opaque native blocks visible as `OPAQUE` events rather than misrepresenting them
as chat text.

## Running the checks

```console
uv run pytest -q tests/test_additional_formats.py
uv run pytest -q tests/test_additional_formats_native.py
uv run ruff check src/session_bridge/formats/pi.py src/session_bridge/formats/opencode.py \
  tests/test_additional_formats.py tests/test_additional_formats_native.py
```

Native tests skip when the exact pinned binary is unavailable. A skip is not evidence that another
version is compatible; each target version should receive its own schema fixture and native oracle.
