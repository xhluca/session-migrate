# Mistral Vibe session format

`session-migrate` reads and writes native Mistral Vibe sessions. The adapter is
pinned to Vibe `2.24.3`, released 2026-08-20, and was checked against official
tag `v2.24.3` at commit `a84be0391bf93e93a4025a5e08e8032ecb587123`.

Unlike the clean-room Antigravity and Cursor adapters, this integration uses a
public Apache-2.0 codebase and its documented local session model:

- [Mistral Vibe repository](https://github.com/mistralai/mistral-vibe)
- [Vibe CLI documentation](https://docs.mistral.ai/vibe/code/cli/work-with-cli)
- [mistral-vibe 2.24.3 on PyPI](https://pypi.org/project/mistral-vibe/2.24.3/)

## Native storage

Vibe resolves its home from `VIBE_HOME`, otherwise `~/.vibe`. A normal session
is a directory below:

```text
$VIBE_HOME/logs/session/
└── session_YYYYMMDD_HHMMSS_<first-eight-uuid-chars>/
    ├── meta.json
    └── messages.jsonl
```

`meta.json` contains the full UUID, working directory, timestamps, title,
message count, last-message fingerprint, and runtime metadata. The JSONL holds
one `LLMMessage` per record. Vibe accepts the full UUID or its first eight
characters:

```bash
vibe --resume aaaaaaaa
```

Because the directory name uses only eight UUID characters, the installer
checks the whole session root for a short-ID collision before creating either
file.

Vibe is a multi-provider client. When native metadata exposes an active model
and its provider mapping, the source reader records both; it never assumes that
the provider is Mistral merely because the client is Mistral Vibe.

## Source projection

The reader snapshots both native files and fails if either changes while it is
being parsed. It validates the metadata UUID, bounded JSON structure, role and
tool shapes, and the source file identity. The following native fields become
portable events:

| Vibe structure | Portable event |
| --- | --- |
| user/assistant `content` | ordered message |
| assistant `reasoning_content` | readable thinking |
| assistant `tool_calls` | linked tool call |
| tool message + `tool_result` | linked tool result |
| inline/file `images` | user image when readable and supported |
| `context_boundary = "compaction"` | compaction summary |
| `meta.json.title` | searchable native title |

Provider-specific `reasoning_payloads` are opaque, not portable reasoning.
Injected runtime messages other than compaction are also opaque. Tool runtime
presentation/duration/cancellation fields are counted separately. Unreadable
or unsupported image references become reason-specific opaque events rather
than silently disappearing.

## Target mapping

The Vibe writer preserves:

- ordered user and assistant text;
- Vibe's own explicit readable `reasoning_content` during a Vibe portable
  rewrite;
- linked function calls and results;
- supported user images as native inline images; and
- compaction summaries as injected compaction-boundary messages.

Thinking from another agent is not promoted into Vibe reasoning merely because
the target has a field for it. Provider signatures/encrypted thinking,
privileged system messages, tool
namespaces, target-unsupported media, branches, and runtime policy/config are
omitted or transformed with exact manifest counters. A generated target must
contain resumable conversation history.

The conversion layer first creates one deterministic validation bundle holding
the metadata object and message array. Installation then publishes the two
native files together in a new mode-`0700` directory; both files and the
external migration manifest are mode `0600`. Existing paths are never
overwritten.

Vibe decides whether it can append by hashing
`LLMMessage.model_dump(exclude_none=True, mode="json")`. The writer mirrors
Vibe 2.24.3's exact default materialization and JSON hashing so the first native
resume appends after the generated byte prefix instead of rewriting it.

## CLI workflows

Import a file-based source into Vibe:

```bash
smigrate import SOURCE.jsonl --format claude --to vibe --cwd "$PWD"
vibe --resume NEW_SESSION_UUID
```

Transfer a Vibe session elsewhere by native ID:

```bash
smigrate transfer VIBE_SESSION_UUID --from vibe --to codex --cwd "$PWD"
```

Use an isolated or non-default Vibe home:

```bash
smigrate transfer VIBE_SESSION_UUID \
  --from vibe --source-home /srv/vibe-home --to pi
```

Or let the catalog index it:

```bash
smigrate catalog refresh --vibe-root /srv/vibe-home
smigrate catalog search "parser cleanup" --format vibe
smigrate transfer --catalog-id RESULT_ID --to opencode
```

Catalog refresh enumerates every native session directory under each selected
Vibe root, indexes the bounded native title/UUID/CWD metadata, and fingerprints
both files for incremental refresh. Search never indexes message or tool bodies.

## Validation evidence

The checked-in gates include:

- a sanitized native two-file fixture with text, image, tool linkage, and
  compaction;
- bundle, malformed-input, collision, permissions, inspection, discovery, and
  catalog tests;
- every ordered Vibe route in the full source/target matrix; and
- an opt-in credential-free native oracle against exact Vibe `2.24.3`.

The native oracle installs a generated session into an isolated `VIBE_HOME`,
uses a loopback synthetic OpenAI-compatible provider, runs the actual
`vibe --resume <id> -p ...` command, and proves:

1. the request contains the migrated post-compaction conversation;
2. Vibe returns and persists the synthetic continuation;
3. the original `messages.jsonl` bytes remain an unchanged prefix; and
4. reparsing finds the appended user and assistant turns.

Run it only with the exact release installed:

```bash
SESSION_MIGRATE_VIBE_BIN=/path/to/vibe \
  uv run pytest tests/test_vibe_native.py
```

The test uses no account credentials and makes no external network request.

## Boundaries

- Compatibility is pinned to Vibe `2.24.3`; a future native schema must be
  revalidated before the pin changes.
- The migrator does not copy `config.toml`, API keys, provider login state,
  agents, tools, MCP servers, connectors, or workspace files.
- Vibe source file-image references are copied only when the referenced file is
  a stable regular file within the media limit. The target embeds the bytes so
  the migrated session does not depend on the source path.
- Conversation content can itself contain secrets. No redaction or encryption
  is performed; treat the target session as sensitively as the source.
